# 导师技术验收对照表

本文件用于对照导师提出的四个技术问题，记录当前项目已经实现、部分实现和尚未实现的能力。

## 当前边界

- 当前系统在本机运行，不接入真实无人机、真实车辆或真实路侧设备。
- 当前不声称已经完成真实 RL / MARL 训练。
- 当前不声称已经满足真实飞控或车控硬实时安全要求。
- 当前重点是验证自然语言意图、DSL 任务契约、多设备协议归一化、冲突消解、动态重规划和可解释决策的闭环。

## 导师问题 1：无人机与汽车通信的频度如何

状态：已实现本机可配置周期通信。

当前实现：

- 本地运行时默认状态同步间隔为 500 ms。
- 前端/后端 API 支持 50 ms 到 5000 ms 的间隔范围。
- `RuntimeAgentStatus` 中包含 `publish_rate_hz`。
- `RuntimeIntentContract` 中包含 `default_status_interval_ms`。
- 通信模式包括：
  - 初始任务契约发布
  - 周期状态同步
  - 事件触发冲突与重规划

证据：

- `source/collaboration/runtime/LocalDDSBroker.java`
- `source/collaboration/runtime/RuntimeDeviceAgent.java`
- `source/server/FrontendApiServer.java`
- `idl/urban_intent_collaboration.idl`

## 导师问题 2：通信协议与报文形式

状态：已实现统一消息模型和 AEP84/STANAG 4586 风格适配。

当前实现：

- 系统内部采用 DDS/ROS2 风格的发布订阅语义。
- 未安装真实 ROS2/DDS 时，使用本机 DDS-compatible Broker 验证。

  - `RuntimeIntentContract`
  - `RuntimeAgentStatus`

  - `ConflictEvent`
  - `ReplanningRequest`

  - `stream_id`
  - `ack_required`
  - `valid_time_ms`
  - `latency_ms`
  - `checksum`
- `ProtocolNativeFrame` 保留原生报文、协议类型、统一 Topic 和兼容性说明。

证据：

## 导师问题 3：不同厂商设备与协议异构

状态：基础能力已实现，但未覆盖全部真实厂商协议。

当前实现：

- 运行时已接入四类协议：
  - DJI-STYLE
  - ROS2-DDS
  - GENERIC-PRIVATE-JSON
  - AEP84-STANAG4586
- `ProtocolAdapterRegistry` 负责根据设备配置选择适配器。
- 不同协议统一转换为 `RuntimeAgentStatus`。
- `ProtocolNativeFrame` 保留厂商原生报文，保证协议适配过程可追溯。
- DSL 层负责任务语义，IDL/DDS 层负责协同消息语义，Protocol Adapter 层负责厂商协议格式。

尚未完全接入运行时主链路的协议：

- MAVLink
- DroneCAN
- V2X
- CAN/ISO-TP

这些协议目前已有独立 Adapter 或转换测试，但尚未全部进入统一运行时设备注册表。

证据：

- `source/collaboration/runtime/ProtocolAdapterRegistry.java`
- `source/collaboration/runtime/ExternalDeviceStatusIngress.java`
- `source/integration/HeterogeneousProtocolAdapterTest.java`
- `source/integration/Aep84ProtocolAdapterTest.java`

## 导师问题 4：实时/准实时条件下方案是否可用

状态：本机准实时协同验证已具备，硬实时未声称完成。

当前实现：

- `QosPolicyModel` 定义可靠性、持久性、deadline、latency budget、历史深度和重试策略。
- `DDSManager` 支持 deadline、latency budget、lifespan 等 QoS 配置。
- `VirtualDDSMessageBus` 支持延迟、过期、丢包模拟。
- AEP84 状态中的 `ack_required`、`valid_time_ms`、`latency_ms` 已保留。
- AEP84 高风险状态可以触发动态重规划，并输出重规划时间线。
- 低置信度、过期或高丢包的 AEP84 状态会被 ConflictResolver 拒绝。

当前不承诺：

- 真实无人机飞控硬实时。
- 真实车辆控制器硬实时。
- 真实链路 ACK/NACK 的完整协议闭环。
- 真实设备安全冗余、急停和人工接管。

证据：

- `source/agent/QosPolicyModel.java`

- `source/dds/VirtualDDSMessageBus.java`
- `source/decision/ConflictResolver.java`
- `source/integration/RuntimeCoordinationPolicyTest.java`
- `source/integration/ConflictResolverTest.java`

## 老师提出的产品边界

老师的要求不是技术指标，而是产品判断标准。当前项目按以下边界执行：

- 场景聚焦：重庆夜间急救物资转运，前方拥堵时由车、无人机、邻车和路侧设备协同绕行。
- 用户聚焦：不写“调度员”这类抽象画像，而是聚焦一个具体操作者，例如急救站值班人员。
- 数据策略：不把模拟数据包装成真实数据；真实设备未接入时，明确标注为本机仿真验证。
- 第一版范围：优先完成“一句话任务 -> 统一设备状态 -> 冲突消解 -> 可解释路线”的核心闭环。
- 表达边界：不把“协议适配器”说成“真实设备已接入”，不把“RL/MARL 接口”说成“已完成训练”。

## 下一步核心工作

1. 增加 AEP84 不同 QoS、ACK 和过期状态下的冲突消解测试。
2. 用 AEP84 报文样本完成本机端到端闭环验证，并输出最终决策解释。
3. 将 AEP84 纳入动态重规划时间线和策略评估报告。
4. 后续再考虑接入真实设备、真实链路和硬件在环。
